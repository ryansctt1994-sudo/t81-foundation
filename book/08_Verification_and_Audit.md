# Chapter 8: Verification and Audit

## 8.1 Formal Verification Methodology

**Status: Implemented**

T81 employs a multi-layered verification strategy, moving from unit tests to formal property verification.

### 8.1.1 The Verification Stack

1.  **Unit Tests (L1)**: Check individual functions and classes.
    *   Example: `tests/cpp/test_T81Int.cpp` verifies `T81Int::add(1, 1) == 1T`.
2.  **Property-Based Tests (L2)**: Generate random inputs to verify invariants (QuickCheck style).
    *   Example: `tests/cpp/test_property_invariants.cpp` verifies $\forall a, b: a + b = b + a$.
3.  **Fuzz Testing (L3)**: Feed malformed inputs to the parser and VM to ensure crash resilience.
    *   Example: `tests/cpp/frontend_fuzz_test.cpp` uses `libFuzzer`.
4.  **Integration Tests (L4)**: Run full end-to-end programs and verify output.
    *   Example: `tests/cpp/e2e_arithmetic_test.cpp`.
5.  **Determinism Gates (L5)**: Verify bit-exact reproducibility across environments.

## 8.3 Property-Based Testing

**Status: Implemented**

We use **Property-Based Testing** to prove that algebraic laws hold for our custom numeric types.

### 8.3.1 The Ring Axioms
The file `tests/cpp/test_property_invariants.cpp` programmatically verifies that `T81Int` and `T81Float` satisfy the axioms of a Ring:
1.  **Associativity**: $(a + b) + c = a + (b + c)$
2.  **Commutativity**: $a + b = b + a$
3.  **Identity**: $a + 0 = a$
4.  **Inverse**: $a + (-a) = 0$
5.  **Distributivity**: $a \times (b + c) = (a \times b) + (a \times c)$

These tests run millions of iterations with randomized inputs (including edge cases like `MaxInt`, `MinInt`, `Zero`) to provide high statistical confidence in correctness.

## 8.4 The Determinism Gate

**Status: Active**

The **Determinism Gate** (`scripts/ci/t81lang_repro_gate.py`) is the final check before any code is merged.

### 8.4.1 Mechanics
1.  **Compilation Consistency**: It compiles a set of 5+ canonical fixture programs (`*.t81`) twice. It compares the binary output of Pass A and Pass B. Any bit difference causes immediate failure.
2.  **Aggregate Hashing**: It computes a SHA-256 hash of the generated bytecode for all fixtures.
3.  **Baseline Verification**: This aggregate hash is compared against a checked-in "Golden Hash". If the compiler logic changes (resulting in different bytecode), the hash will drift, and the build will fail. This ensures that compiler changes are intentional and audited.

### 8.4.2 Traceability
When the gate passes, it outputs:
```text
[PASS] T81Lang gates passed: fixtures=5 hash=a7f92b...
```
This hash is recorded in the CI logs, providing an immutable record of the compiler state for that release.
