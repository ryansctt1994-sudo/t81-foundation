# Глава 8: Ядро безопасности Axion

## 8.1 Формальное определение

**Статус: Реализовано и протестировано**

**Ядро Axion** — это супервизор на основе возможностей (capability-based), который управляет выполнением T81VM. Он обеспечивает строгое разделение между *механизмом* (опкоды TISC) и *политикой* (ограничения безопасности).

Формально Axion — это функция $\mathcal{A}: (S, I) \to \{ \text{Allow}, \text{Deny}, \text{Warn}, \text{Defer} \}$, где $S$ — текущее состояние VM, а $I$ — предлагаемая инструкция.

## 8.2 Модель политик

**Статус: Реализовано**

Политики Axion — это декларативные наборы правил, которые определяют допустимый конверт выполнения.

### 8.2.1 Грамматика политик
Документ политики состоит из:
1.  **Директивы**: Глобальные ограничения (например, `max_stack_depth`, `max_cycles`).
2.  **Системные вызовы**: Гранты разрешений для определенных операций (`io.net`, `fs.read`).
3.  **Лимиты уровней**: Максимально допустимый Когнитивный Уровень.
4.  **Этика**: Конфигурация для Девяти Принципов ($\Theta_1 \dots \Theta_9$).

```yaml
policy:
  version: "1.0"
  directives:
    max_stack_depth: 1024
    max_cycles: 1000000
    allow_recursion: true
  syscalls:
    - allow: "io.print"
    - deny: "fs.write"
  tiers:
    max_tier: 3
```

## 8.3 Перехват инструкций

**Статус: Реализовано**

T81VM вызывает Axion перед выполнением чувствительных инструкций. Этот механизм перехвата является основной точкой контроля.

### 8.3.1 Интерфейс системных вызовов
VM вызывает `eval_axion_call` (`src/vm/vm.cpp`) с контекстом, содержащим:
*   `caller`: Исполняющий модуль.
*   `syscall`: Идентификатор операции (например, `kAxRead`, `kMetaWrite`).
*   `payload`: Аргументы или целевые адреса.
*   `pc`: Текущий счетчик команд.

### 8.3.2 Вердикты
Axion возвращает структуру `Verdict`:
*   **Allow** (Разрешить): Операция выполняется.
*   **Deny** (Запретить): Операция блокируется, и VM вызывает прерывание `SecurityFault`.
*   **Warn** (Предупредить): Операция выполняется, но предупреждение записывается в трассу.
*   **Defer** (Отложить): Решение откладывается до логики более высокого уровня.

## 8.4 Журнал аудита (Трасса)

**Статус: Реализовано**

Каждое значимое решение Axion записывается в **Трассу Axion**. Этот журнал представляет собой последовательность записей `AxionEvent`, доступную только для добавления.

> **Ссылка**: См. `include/t81/axion/api.hpp` для определений `AxionEvent` и `Verdict`.

## 8.5 Когнитивное продвижение

**Статус: Реализовано**

Axion управляет эскалацией привилегий через **Когнитивные Уровни**. Когда программа пытается превысить лимиты своего текущего уровня (например, глубина рекурсии > 81), VM проверяет политику. Если разрешено, уровень повышается; в противном случае происходит прерывание.

> **Верификация**: См. обработку `Opcode::Call` в `src/vm/vm.cpp`.

## 8.6 Модель возможностей

**Статус: Реализовано**

Axion реализует модель объектных возможностей (OCap). Ресурсы (файлы, сетевые сокеты) представлены как неподделываемые дескрипторы (хендлы).
*   **Создание**: Только авторизованные системные вызовы могут создавать дескрипторы.
*   **Использование**: Опкоды работают с дескрипторами, а не с сырыми адресами.
*   **Отозвание**: Дескрипторы могут быть отозваны политикой в любое время.
